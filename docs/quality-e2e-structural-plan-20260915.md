# 端到端失败的结构性分析与解决方案规划

日期：2026-09-15 ｜ 触发：B 启用后 C01 两次端到端均失败（形态不同）
方法：`grounded-ai-new`（幻觉诊断树 + 拒答原则）× `plan-backend-new`（架构/降级路径）× `vet-plan-new`（五问对抗）

---

## 一、分析：为什么会"整轮零输出"（且两次形态不同）

### 1.1 量化（1e4 离线 5 争点 × 2 采样，零成本）

| 争点 | 通过率 | 失败形态 |
|---|---|---|
| 1 / 2 / 3 / 5 | **1.00** | — |
| **4** | **0.50** | `UNSUPPORTED_CITATION`（`cited_not_retrieved`） |

⇒ **端到端（渲染须全部争点通过）预测通过率 = Π pᵢ = 0.50**。
实测 0/2：P(0/2 \| p=0.50) = 0.25 ⇒ **与观察不矛盾**（n=2 不足以断言系统缺陷）。

### 1.2 失败形态的共同点（关键）

| 轮 | 形态 | 机制 |
|---|---|---|
| 1e4 端到端 | `UNKNOWN_FACT_ID` | 该争点 payload **只有 1 条 fact**（"没有补偿"），模型需要"入职年限/平均工资"（在 `unknown_facts`，**不可绑**）→ **编造 fact_id** |
| 1e5 端到端 | `UNSUPPORTED_CITATION` | 引用**检索池外**的法条（`cited_not_retrieved`）→ **凭常识引用** |

⇒ **同一根因**：**模型需要 payload 里没有的东西（事实/法条）→ 编造 → 防线正确拦截**。
⇒ 这是**防线在正常工作**（不该放宽），但**代价是整轮零输出**。

### 1.3 结构性放大

`render` **逐争点串行、首个失败即停** ⇒ 单点 90% 的争点在 5 争点下只剩 ≈ 0.9⁵ ≈ **59%**。
**「离线单点率」与「端到端成功率」口径不可混比**（本会话第三次同类口径问题）。

### 1.4 与 §4.2 的关系（关键论证）

- §4.2 要求：「回答覆盖：回答用户选择的全部争点；**相关事实不足时说明条件，不跳过问题**」
- grounded-ai 原则：「低置信时明确**「未收录/建议核对」**，宁可拒答不硬编——错放代价 > 错杀代价」
- **现状**：`final_chars=0` = **整轮零输出** ⇒ 这**不是**上述"有信息量的拒答"，
  而是**把其余能回答的争点也一起跳过了** ⇒ **与 §4.2「不跳过问题」直接冲突**
- ⚠️ 但 §4.2 同时禁止：「不得通过删除坏 claim、自动替换引用、**降低覆盖率要求**来制造通过」
  ⇒ 「部分交付」必须**不改变验收标准**（未覆盖争点仍记 FAIL/REVIEW），仅改变**交付形态**。

## 二、方案空间（design it twice）

| 方案 | 内容 | 优点 | 代价/风险 |
|---|---|---|---|
| **A 争点级显式降级**（架构） | 某争点校验不过 → **不整轮失败**，该争点记「无结论 + 原因」，其余争点正常交付；终稿显式标注"未覆盖争点及原因" | 直击 §4.2「不跳过问题」；E2E 通过率不再被单点拖垮；**用户拿得到东西** | ⚠️ **必须同步改 verifier**（`verifier.py:289` 也要求每 issue 有 claim，否则只是把失败推后——**B 的教训**）；改动面含 writer/verifier/service 覆盖率统计/前端展示 |
| **B 提升单点成功率**（prompt） | 第 4 次 prompt 补丁：明确"**payload 里没有的事实/法条一律不得引用；无则留空或条件化**" | 面小、同族先例（0d75f37/e5c5392） | **边际收益递减**（已 3 次补丁，模型仍违反）；可能诱导"什么都不写"（回到 A 前的零 claim 形态） |
| **C 提高 payload 完备度**（planner/检索） | 争点4 需要"入职年限/平均工资"（unknown）+ 相关法条（未召回）→ 补检索 / planner 产出更聚焦争点 | 治本方向 | 召回 43.4% 已是**四族否证后的上限**；planner 改契约影响面大 |
| **D 接受现状并记录** | 把 C01 记为未达标，保留证据，转其他任务 | 零风险 | §4 第 1 优先级未达成；E2E ≈50% 意味着**一半案例用户拿零输出** |

## 三、我的推荐与理由

**推荐 A（争点级显式降级）为主 + B 为辅**，理由：

1. **A 有 §4.2 明文依据**（"事实不足时说明条件，不跳过问题"）——现状的"整轮零输出"恰恰是**跳过问题**；
2. **A 是唯一能改变 E2E 通过率量级的杠杆**：B/C 都在"提升单点率"，而单点已 90%；
   在 5 争点串行结构下，单点从 90%→95% 只把 E2E 从 59%→77%，而 A 可直接把"是否有输出"与单点脱钩；
3. **B 的教训必须前置**：**改 writer 必须同步改 verifier**，否则只是把失败推后（已在 B 项上踩过一次）；
4. **C 的黄金期已过**（召回四族否决）；**D 在产品上不可接受**（一半案例零输出）。

**但 A 触 §4.2 红线，必须由你明确定界**：
- ✅ 允许：未覆盖争点在终稿中**显式列出 + 说明原因**，验收**仍记该争点 FAIL/REVIEW**
- ❌ 不允许：把"部分覆盖"当作通过、或降低验收的覆盖率要求

## 四、vet-plan-new 五问自审（对方案 A）

1. **模块边界自然吗**：A 的改动落在**既有三个模块**内的失败语义收口（`writer.render` 的失败传播、
   `verifier.verify` 的 deficient 判定、`service` 的覆盖率统计）——不新增模块；关键是**三处语义必须一致**。
2. **有没有更优解**：已对比 B/C/D；A 的替代是"减少争点数"（planner 侧，属 C）——
   但争点数由案件复杂度决定，**不应为通过率而人为减少**（会掩盖问题）。
3. **会被哪个历史教训击穿**：
   - **B 的教训**（只改 writer 不改 verifier → 失败推后）→ 本方案把"同步改 verifier"写成前置条件 ✓
   - **§4.2 降覆盖率红线** → 已明确"不改变验收标准"✓
   - **静默降级**（`[fz]` 教训）→ A 必须**显式标注**未覆盖争点，不得静默 ✓
4. **事实可查吗**：本方案全部数字来自本会话实测（`quant-1e4.json`、1e4/1e5 的 runner 日志与账本）；
   唯一推断是"E2E ≈50%"，已标注为**推断**并给出 P(0/2) 检验。
5. **DoD 带可测指标吗**：
   - 端到端 C01：`final_chars>0 且 agent_completed=True`；
   - **且**终稿必须**显式列出未覆盖争点**（若有）——可自动检查（终稿含未覆盖争点清单）；
   - **且**验收仍按 §4.2 六维度，未覆盖争点记 FAIL/REVIEW（不被"有输出"掩盖）；
   - 端到端通过率须用**统计口径**（§5）：连续跑 n 次报通过率，不用单次转绿下结论。

## 五、若选 A：实施骨架（待批准后再细化）

1. `writer.render`：单争点 FAIL_SAFE → 收集 `uncovered_issues: [(issue_id, reason_code)]`，**不中断**；
   全部争点都失败时仍 FAIL_SAFE（无内容可交付）
2. `verifier.verify`：未覆盖争点**不得**触发整轮 FAIL_SAFE；改为**记录 + 该争点记 REVIEW**
3. `service`/渲染层：终稿追加"未覆盖争点及原因"章节；覆盖率统计区分"已覆盖/未覆盖（带原因）"
4. 前端：失败态与"部分交付"区分展示（沿用既有结构化失败态）
5. 测试：单点失败→其余交付（新）／全部失败→仍 FAIL_SAFE（回归）／未覆盖争点必现于终稿（新）
