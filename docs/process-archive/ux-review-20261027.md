# 以“讨厌这个应用的用户”视角做的一轮 UX 审查与改进（2026-10-27）

> 方法：先把自己当成一个**已经付费、但被一次服务中断惹毛**的用户，列出最想摔手机的 7 件事；只修能在本轮真实验证的高影响项，其余明确挂账。证据在 `dispatch-output/ux-review-20261027/`（审计 JSON + 两张真实渲染截图）。

## 1. 我讨厌它的 7 件事

1. **失败的回答看起来像正常回答**：历史里有 43 条“服务暂时无响应，请稍后重试。”，界面不给错误态、不给重试，用户只能自己重打一遍问题。
2. **任何失败都不能原地重试**：网络错误/空答后，问题还在，但没有“重试”入口。
3. **截图里的答案像官方结论**：免责声明只在输入框底部，答案本身没有“AI 生成”标记。
4. **不能干净地复制答案**：想粘到微信/文档，只能手动选中整段（含按钮/法条样式）。
5. **键盘用户打不开法条**：正文里的《法》第X条是点击才弹卡的 span，Tab 聚焦不到、Enter/Space 无反应。
6. **看不到条文版本/状态**：参考条目只写法名+条号，不知道是现行、何时施行、何时失效；法律问题里这是硬伤。
7. **历史会话没有搜索/重命名/导出**：会话一多只能翻列表；本轮已补搜索、重命名与 Markdown 导出（见 §2）。

## 3. 仍然没做（不是漏了）

- **PDF 导出**：本轮做了 Markdown 导出；PDF 需要排版/中文字体/分页，属于独立交付。
- **深色模式 / 读屏软件专业审计**：本轮做了 390×844 移动端真实渲染；读屏软件、全键盘链路、对比度没有专业无障碍测试。
- **法条基准日的完整历史版本**：控件已做，但库内 10854 条只有 **588 条带 `effective_from`、0 条带 `effective_to`**；未标注日期的条文按现行处理，控制项 tooltip 已写明。
- **现网 qa_pairs 原地恢复演练**：备份恢复演练只证明“可重建”，没有写现网（需另一次写授权）。
- **登录/注册**：注册当前关闭（产品决定）；本轮没有改鉴权流程。

## 5. 已知限制 / 坑

- 失败识别是**字符串判据**（历史占位与客户端兜底两句）；后端若改文案要同步 `chatErrors.ts`。
- 参考条目的版本 tooltip 依赖后端 `meta.sources` 带 `effective_from/effective_to/status`；字段缺失时显示“版本日期未标注”，不会编造日期。
- 重试会替换失败回答并**重新走一遍检索/生成**；文件/图片的历史消息不提供重试（原文不可从历史复原）。
- **`next build` 与 `next dev` 共用 `.next`**：dev 在跑时执行 build 会把 dev 的模块文件覆盖，页面报 500/MODULE_NOT_FOUND。先停 dev，或 build 后删 `.next` 重启 dev（本轮实测踩到一次）。
- 视觉审计覆盖 1280 桌面与 390×844 移动；读屏软件/全键盘链路未做专业无障碍测试。
- 基准日控件只按库内已标注日期的条文过滤（588/10854 有 `effective_from`，0 条有 `effective_to`）；未标注的按现行处理，不要把它读成“完整历史法版本”。
