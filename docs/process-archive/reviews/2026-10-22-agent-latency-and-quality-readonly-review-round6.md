## 3. A6-01：事实覆盖判定过宽，写作输入可能漏掉关键事实

**位置：** `backend/agent/runtime.py:486–499`、`:623`；`backend/agent/writer.py:68`、`:297`。

覆盖检查使用 `q in target or target in q`。只要某条引用是用户分句中的任意片段，就认为整个事实分句已覆盖。引用来源校验能确认“来自原文”，却不能确认“保留了完整事实”。当缺陷清单为空时，分解修复环直接返回，不再补全。

隔离输入：

> 我每月工资8000元，工作已经满三年，公司没有签订劳动合同。能否要求赔偿？

构造合法分解结果：争点为“公司应当承担哪些责任？”，事实引用只有“工资”“工作”“合同”，未知事实为空。

实际函数结果：

- `non_verbatim=[]`、`uncovered=[]`，分解只调用一次，没有事实修复。
- Writer facts 只有三个关键词；金额 `8000`、工龄 `三年`、否定事实 `没有签订` 都不在该写作投影中。
- 对照输入采用三条完整事实分句，同样通过校验，三项关键内容均进入 Writer。
- 完整原问题仍保存在 `state.user_question`，并非数据库原文丢失；但 `WriterPayload` 没有完整原问题字段作为这一路的兜底。

**影响：** 当分解模型给出这类合法但过短的引用时，后续写作缺少会影响分析的事实，服务端却未报告覆盖缺口。本轮证明的是可接受输入与确定性投影缺口，没有证明生产模型已经输出此类分解，也没有生成真实法律错误答案。

**最小方向：** 用事实分句或原文跨度的实际覆盖来识别缺口；保留数字、否定词和限定条件。优先复用已有原文分句与来源信息，不为此新增一个 LLM 评判器。若增加可信原文投影，必须保留事实/未知事项的区别与现有引用验证。仅增加引用最短字符数不足以解决问题。

**建议验收：** 上述短词案例必须识别缺口或让完整事实安全进入写作输入；完整分句对照仍通过；补齐后仍校验逐字来源，不把推测变成用户事实。

## 4. A6-02：SSE 在完成后才开始，首事件等待接近整轮耗时

**位置：** 当前 `backend/main.py:880`、`:893`、`:1930`、`:1962`、`:2022`、`:2034`；`backend/agent/chat_integration.py:78`；`frontend/lib/api.ts:169–182`。

新请求和恢复请求都先 await 完整 Agent service，再创建 `_agent_streaming_response(result)`。序列化函数把已完成的结果转成 status、verification、token、final 等事件。因此即使响应格式是 SSE，也没有在分解、检索和写作期间向客户端发送阶段进展。普通快车道的预发送状态不能据此推定 Agent 也具备相同行为。

前端在 fetch 前启动 180,000ms 看门狗，收到数据才重置。隔离运行实际 `streamChat`，让替身 fetch 保持等待，并主动触发虚拟计时器，得到：fetch 已 abort、错误为“连接超时，已中断”、函数已返回、计时器已清理。

**触发条件：** 命中 Agent 路径，且首次返回数据前超过前端阈值。此时客户端可能在服务端仍工作时放弃等待。这里没有真的等待三分钟，也没有用浏览器或网络复现生产链路。

**最小方向：** 在工作开始时发送 accepted/phase 等非正文事件，并提供合理心跳；继续在校验通过后才发布法律正文。同时配置整轮服务端截止时间。只延长前端超时，不能解决资源消耗和缺乏进展反馈。

**建议验收：** 用可控慢依赖检查首事件、阶段进展、最终结果三个时间点；确认未校验草稿不提前输出；确认客户端取消后服务端停止后续阶段。

## 5. A6-03：检测断开与停止工作之间存在明显空档

**位置：** `backend/agent/service.py:280`、`:305`、`:335`、`:428`、`:529`、`:561`；当前 `backend/main.py:893`。

service 首次取消检查位于 `build_initial_state` 和 `controller.run` 之后。控制器首轮检索批处理内没有对应的取消轮询；同步 LLM invoke 也没有从该接口获得取消信号。

隔离执行实际 service，传入始终返回 True 的取消函数；分解和控制器各由 20ms 替身实现。观察顺序为：

`decomposer_started → controller_started → cancel_check → CLIENT_DISCONNECTED`

本次耗时 45.59ms，只用于证明执行顺序。没有用真实持久层验证取消后的状态写入。

**影响：** 用户关闭页面或前端超时后，仍可能先完成已经进入的分解、检索批次，继续占用模型并发或工具资源。0.1 秒断开轮询只是检测频率，不是工作停止时间上限。

**最小方向：** 在启动分解、控制器及每项新外部工作前检查取消，并传递剩余整轮时间。已有同步调用不能靠设置 Event 强制结束，应约束等待与底层超时，明确终态持久化规则。保持所有权、版本 CAS 与失败关闭校验。

## 6. 回复耗时由哪些部分构成

对当前串行路径，可用于排查的近似分解为：

`首事件等待 ≈ 排队/准备 + 分解 + 各争点检索耗时之和 + 按需规划 + 各争点写作耗时之和 + 校验/渲染/持久化`

这不是生产预测公式；失败重试、补充检索、澄清和降级会改变路径。

### O6-01：线程池存在，不代表同一请求的争点检索并行

`backend/agent/controller.py:940` 的批次循环在 `:1017` 同步等待 gateway。实际方法接入每项固定 20ms 的替身工具：

| 争点数 | 实际调用数 | 本次观察耗时 | 调用是否重叠 |
| --- | --- | --- | --- |
| 1 | 1 | 21.17ms | 否 |
| 3 | 3 | 61.59ms | 否 |
| 5 | 5 | 102.73ms | 否 |

这些单次微型观察证明调度方式，不代表真实检索耗时或吞吐量。工具执行池的 4 workers / 8 outstanding 约束跨任务容量，不会自动并行这段调用循环。

`backend/agent/service.py:435` 也按争点逐个写作，部分分支在 `:446` 重写一次。逐争点写作是现有设计取舍，不能直接判为 bug。

**优化顺序：** 先采集阶段耗时，再考虑对独立检索使用已有容量控制下的有界并发，按稳定顺序合并结果。不要共享并发数据库 Session，也不要一次性把写作、状态提交和所有工具改成并行。这一项与旧 harness 审查 H06 重合。

### O6-02：工具超时不等于底层线程已停止

`backend/tools/gateway.py:51` 的 BoundedExecutor 和 `:265` 的 `future.cancel()` 已有容量边界与取消尝试。

隔离建一个 worker、一个 outstanding 的实际执行器，让已启动任务等待 Event。等待方超时后，`cancel()` 返回 False，outstanding 仍为 1，新任务被拒绝；释放 Event 后 outstanding 回到 0。

这是同步线程的容量边界，不是无限队列证据。尚未执行的排队任务可以取消；不能据此声称所有超时任务都会继续运行。检索工具已有 deadline 传播，部分 rerank/rewrite 会依据剩余时间跳过或限制调用，应保留这些措施。

**建议：** 观察超时后槽位释放时间，区分排队、运行与被拒绝；对底层依赖设置与整轮剩余时间一致的限制。不要通过无限增加线程掩盖问题。

### O6-03：调用次数有边界，但并不等于整轮秒数有边界

- `backend/llm_registry.py:386–387` 配置默认 timeout 120、max_retries 3；这是客户端配置，不是整轮 120 秒截止时间，也不能简单当作固定总耗时。
- `backend/agent/runtime.py:285` 的 failover 每次逻辑 invoke 新建 tried 集合；一次调用内同一模型最多尝试一次。合成三个模型均返回 503，连续两次逻辑 invoke 得到 `m1,m2,m3,m1,m2,m3`。没有执行 SDK 内部重试。
- schema fallback 仅针对明确能力拒绝；不能把任何失败都算成“绑定一次再普通调用一次”。事实修复、Planner 解析修复和条件性 Writer 重写也必须分别计数，不能把不同分支的最大次数机械相乘。
- transport 成功分支直接返回；失败切换有事件，不等于成功调用也有耗时事件。日志字段白名单允许 duration，也不证明该字段已在成功路径产生。

**建议：** 建立整轮截止时间和按剩余时间控制的重试预算；优先补齐成功阶段耗时。不要未经分析删除所有重试或增加另一套复杂调度系统。

## 7. 最小测量与修复次序

1. 修复 A6-01 并保留来源校验；这是可独立确认的质量缺口。
2. 记录实际命中路径、首事件时间、最终完成时间；为 Agent 提供非正文进展事件，区分“用户知道正在处理”和“拿到可信答案”。
3. 补齐阶段前取消检查和整轮时间预算；明确停止后的状态与槽位释放。
4. 用阶段数据决定是否并行独立检索；评估一次变更，避免同时改模型、提示词、检索与并发而无法归因。

建议最小指标：排队、分解、检索、写作、校验、持久化耗时；争点数；逻辑调用与实际供应商尝试数；首事件/最终结果延迟；超时与取消原因；取消后资源释放延迟；成功/澄清/降级/失败比例。使用不含原始问题与隐私文本的关联标识。生产 p50/p95 必须采集后再报告。
