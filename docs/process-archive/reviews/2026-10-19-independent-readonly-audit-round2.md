## 3. 候选仍存在的六项静态风险

以下路径为各对象内相对路径；M/C 绝对根目录见 §1。

### R15：半截失败输出没有及时失效

- M：backend/main.py:2438–2465；合同同族约 2233–2242。
- C：backend/main.py:2916–2942；合同同族 2661–2672。
- 触发序列：第一个模型产生一段正文后抛出可重试异常；后两次尝试正常结束但都返回空内容。
- 源码链：失败回调设置 restart_pending；只有下一条非空 piece 到来，外层才清空 chunks 并发 restart。后续全空时这段代码不执行；最后 join(chunks) 仍得到第一个失败模型的半截。
- 后果：跳过空答处理，可能正常发 DONE、落库为成功答案。合同路径还可能标记完整报告。满足后续条件时可缓存；配额也可能记到最后尝试的模型。不是声称每条半截都必然通过自检或缓存。
- 最小方向：在一次尝试失败时使该尝试产物失效，并通知客户端；最终成功必须来自完整结束的尝试。仅在有下一条正文时才处理 restart 不足以保证这一点。
- 验收：合成“半截→503→空→空”；检查 SSE 重置、最终状态、落库、合同完整标记及缓存。再测“半截→503→完整后备答案”，只保留后备正文。
- 置信度：高，静态组合路径完整；未动态复现。

### R16：think 解析状态跨尝试污染

- M：backend/rag_chain.py:280–295。
- C：backend/rag_chain.py:421–433。
- 源码链：ThinkStripper 在 configs 循环外创建，每次尝试共用实例。
- 触发：首模型输出未闭合的 <think>分析中，随后连接失败；后备模型输出正常正文且没有结束 think 标签。
- 后果：解析器仍处于思考区间，后备正文被吞。后续重试继续受影响，可能报空答或多执行非流式兜底。
- 最小方向：每次独立生成尝试初始化自己的解析状态；同一次尝试内继续保留跨 chunk 解析能力。
- 验收：未闭合 think 后换模型，正常后备正文必须输出；同次流跨 chunk 标签仍正确过滤。不能只测单次流标签拆分。
- 置信度：高；未动态复现。

### R17：整法导入失败会先丢原种子条文

- M：backend/scripts/import_docs.py:89–108；主循环约 162。
- C：backend/scripts/import_docs.py:109、119；主循环约 177；写入异常处理 backend/knowledge_service.py:178–185。
- 源码链：查同 source、article 的 seed→删除 seed→调用 add_chunks 写新条文。新写入的嵌入或存储异常会向上抛出，没有恢复已删除内容。
- 后果：新条文未成功入库，旧文已经删除，影响后续精确与模糊检索。这是失败路径的数据保护问题，不依赖某部法律的具体文字。
- C 的已有防护：默认预览、显式 --write、目标路径守卫；它们缩小实写触发面，但不能保护明确实写时的先删后写顺序。
- 最小方向：复用已有先写成功再清旧模式；验证写入完整性与重跑行为，删除后使相关缓存失效。不能用“异常时提示重跑”代替保留原数据。
- 验收：隔离集合中预置 seed，注入嵌入/写库失败，旧条文仍可查；成功替换和重跑不能产生错误重复或漏文。
- 置信度：高；未在真实库操作。

### R18：不同法律同正文被融合成一条

- M：backend/retrieval.py:773–775、952–968。
- C：backend/retrieval.py:927–929、1182、1187。
- 源码链：_doc_id 只返回 page_content；向量/BM25 候选使用 pool.setdefault(did, document)。
- 触发：两条资料有不同 source/article/version，但正文相同，均通过过滤并进入候选。管理员分别录入知识可形成这一状态；正文不自动包含完整来源身份。
- 后果：后到资料的法名、条号或版本元数据丢失，重排无法恢复。精确检索可保留不同来源，模糊融合却只留下一个，出处还可能随召回顺序变化。
- 最小方向：使用稳定片段身份，或让融合键纳入来源、条号、版本与正文。要求同一资料的向量/BM25 双路仍可合并，避免修成全部重复。
- 验收：同正文不同法名、不同版本均保留；同一片段双路只保留一次。输入使用合成法律资料，不宣称这是现役语料统计结果。
- 置信度：高；未动态复现。

### R19：配额校准无法撤销运行期置尽

- M：backend/llm_registry.py:666–677、707–720。
- C：backend/llm_registry.py:916、960–962；管理调用 backend/main.py:3604。
- 源码链：mark_depleted 将剩余额度加进 runtime_used；calibrate 只修改 initial_used，公式为 max(0, total - remaining - runtime_used)。
- 确定性示例：total=1000、initial=0，置尽后 runtime=1000；管理员校准 remaining=500，new_initial 仍为 0，quota_left 仍为 0。
- 后果：接口正常返回却未按控制台读数恢复模型。持久化只写 initial，也不能保证重启后的剩余额度等于提交的 500；具体重启数值取决于此前真实持久运行用量。
- 最小方向：校准完整配额基线，令内存与持久状态一致。避免把“不可用标记”混成无法校正的实际用量。
- 验收：置尽后校准、运行估算过扣后校准、重载后余量与路由恢复。分别检查内存和隔离账本，不只检查接口 200。
- 置信度：高，公式可直接推导；未执行测试。

### R20：轻量升级的两次用量都记到旗舰

- M：backend/main.py:1485、1487、2377。
- C：backend/main.py:1864、1866、2829；路径准入约 2387。
- 源码链：轻量 L 失败、旗舰 F 重答后，结果 key 为 F，usage 为 L+F；调用处只执行 deduct(F, total)。
- 示例：L 使用 100、F 使用 200，账面却为 L=0、F=300。示例是算术说明，不是实测 token 数。
- 适用边界：默认角色表无 text/light，默认配置下该路径不可达。合法自定义配置提供 light 角色，且升级到不同旗舰后触发；不可把它描述为所有当前请求都错记。
- 最小方向：每次调用按实际 key 分别记账；最终展示模型与调用用量归属分别表达，避免多层重复扣减。
- 验收：自定义 light/flag 合成模型与 usage，轻量失败升级后两份账分别正确；再验证不升级、同 key 与失败路径。
- 置信度：高；未动态验证。与第一轮 R09“Agent 不记成功用量”是不同缺陷。

## 4. 主目录 QA 的四项发现及候选差异

### R21：个人上下文被沉淀为公共答案

- M：backend/main.py:469–480 把个人摘要/历史加入生成；1011–1015 不排除 recent、summary 或 image，以 user_text 原始追问作 QA 问题；backend/knowledge_service.py:398–409 高分自动写共享 QA；main.py:1261–1281 直返没有个案身份检查。
- 示例序列：A 先提供个人事实，再问“按我的情况，应赔多少？”；模型结合历史作答；原始追问作为全局 QA 问题。B 新会话输入相同追问，可命中并收到 A 的个案回答。
- 影响：错误个案结论可能传播；若模型复述历史中的金额、雇主或姓名，则可能泄露信息。尚未动态验证模型是否实际复述敏感内容，因此不声称发生过真实泄露。
- M 建议级别：P1。
- C 防护：backend/knowledge_service.py:580–585 无条件建 pending，无自动向量发布；643–654 人工批准才写。原自动传播链已断。
- C 残留：backend/main.py:1262–1268 仍可能以原始追问收集个案候选；人工批准前的公开资格、脱敏和自包含性仍需检查。这是受人工审批条件限制的风险，不等同原自动泄露等级。
- 最小方向：个人上下文依赖答案不能直接变公共答案；先明确共享资格。只把 question 改成 rewritten 不能单独证明隐私安全。
- 验收：合成双用户多轮与图片上下文，验证公共读取面；C 同时验证 pending 不可公开，批准前保留足够审核信息。

### R22：拒绝记录没有真正撤回共享答案

- M：backend/knowledge_service.py:443–464；backend/main.py:3016–3024。批准后向量已写；rejected 分支只改 SQL status，读侧不核验该状态，也不失效答案缓存。
- 触发：approved→rejected，管理 API 成功；之后公开 QA 查询或 prompt 注入仍可使用原内容。
- C 防护：knowledge_service.py:662–664 标记 rejected/revoked 并加版本；675–677 提交后失效。qa_eligibility.py:187–194 拒绝 revoked；knowledge_service.py:514 实际调用资格选择；main.py:2490–2493 在 QA 首正文前复核，2452–2453 在答案缓存输出前检查依赖。
- 结论：M 为 P2；C 已见对应防护，不能重复登记为“候选没有撤回检查”。
- 验收：批准→公开查询→撤回→QA/答案缓存/prompt 三出口复查，包含在途请求。仍需动态证据，源码防护不等于验收通过。

### R23：向量先写、SQL 后提交，失败状态可能已公开

- M：backend/knowledge_service.py:450–462；自动收录同形于 399–412。
- 源码链：add_qa_pair→invalidate→改状态→commit。失效或 SQL 提交失败时，向量已经持久存在；无候选绑定资格检查，也无补偿。
- 后果：管理请求失败，公开读取面却可能已经得到答案；重试批准产生重复向量。
- C 防护：knowledge_service.py:379–380 写 qa_candidate_id；qa_eligibility.py:191–196 拒绝缺行或 approval_source unknown；因此首次批准提交失败留下的向量，原直接公开链受到阻断。
- C 残留：knowledge_service.py:644 每次批准新建 UUID；647–654 先写向量、675 才提交。重复批准或失败仍可留下孤儿/重复向量，没有证明存储原子性已完成。已批准记录再次批准失败的残留也须单独核对。
- 结论：M 为 P2；C 的“未批准发布”已有防护，剩余项应按存储一致性/幂等性单独评估等级。
- 最小方向：稳定身份、幂等发布和可恢复状态；以已提交资格决定可服务性。不要为追求两个存储的表面同步而引入不必要框架。
- 验收：分别注入 invalidate、commit、向量写入失败，检查公开资格、孤儿和重试幂等；不能只看 SQL status。

### R24：自检失败经持久 QA 通道重新获准

- M：backend/main.py:2546–2581 自检失败只加提示；2621 默认 curate=True 调 _post；1011–1015 沉淀只看检索分和 should_curate。backend/curation.py:18–20 只检查长度、引用形式与检索分；高分可自动发布。
- 触发：检索相关性高，但生成答案含自检未通过的引用。答案缓存写闸拒绝它，持久 QA 沉淀却不消费该失败结论；读侧校验的是 evidence 中检索条文，不能替代检查答案实际引文。
- 后果：已经识别为失败的输出可能作为可信 QA 重复服务。这里不是反对有历史授权的自动收录策略，而是指出质量失败结论没有跨发布边界传递。
- C 防护：knowledge_service.py:580–585 pending-only 阻断自动发布；main.py:1262–1268 仍可把此类内容入待审。
- 结论：M 为 P2；C 不再存在原自动批准链。是否禁止质量失败内容进入待审，需要既有产品规则支持，不能据本报告强行新增规则。
- 最小方向：共享复用资格应消费已有质量、版本、降级信号；人工审核需要看见这些信息。
- 验收：合成检索高分、自检失败回答，通过旗舰/轻量生产入口观察公开资格；C 确认只待审且无绕行自动发布。

## 5. R25：真实模型门禁可能在缓存答案下通过

- M/C：backend/scripts/smoke_citation_full.py:69–89，只发送 question 并累加 content。
- schemas.py:57 提供 no_cache，默认 False，注释用途就是评测真实 LLM。主目录 main.py:2037、2063、2092，以及 C main.py:2408、2454–2486，在模型生成前允许答案或 QA 直返。
- 影响边界：脚本仍可证明 API 返回文本包含所需引用；它不能单独证明本次调用了真实模型，更不能证明轻量自检失败后真的升级。脚本文案将其称为含 LLM/轻量升级门禁时，证据强度不足。
- 进一步观察：chat 不强制看到正常完成标志，也不拒绝 error/restart 事件，只收 content。含正确引用的半截随后发生错误时，也存在被内容断言接受的空间；需合成 SSE 独立验证，不把它当成本轮已动态复现。
- 最小方向：明确区分“面向用户的 API 内容冒烟”与“真实生成/升级验证”。后者显式绕过直返缓存、记录实际路由与调用证据，并校验完整成功结束；不能仅把脚本标题改成“全量通过”。
- 验收：合成缓存命中、真实生成、升级和流失败场景，检查各自被判定的范围。不需为了证明确定性门禁缺口消耗真实模型费用。
- 分级：当它被用于真实模型或升级验收时 P2；若用途仅为内容冒烟，则应收窄结论，不能将“没有强制调用模型”本身视为产品缺陷。
