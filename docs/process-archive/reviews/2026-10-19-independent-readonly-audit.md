## 3. 逐项证据、建议与验收要点

### R01：旧 JWT 随用户 ID 复用而获得新用户身份

- 位置：backend/models.py:12；backend/auth.py:45、65；backend/main.py:2871、2883；backend/database.py:9。
- 静态证据：User.id 是 Integer primary_key，未配置 SQLite AUTOINCREMENT；管理员接口硬删用户；JWT 的身份主体 sub 为数字 ID；鉴权只按 sub 读取当前 User，并检查存在性和 is_active。源码迁移没有为 users 增加防复用身份字段。
- 触发：账号 A 持未过期令牌；管理员删除当前最大 ID 的 A；之后创建 B，SQLite 可分配相同 ID。A 的旧令牌因此查到 B。
- 影响：可能跨用户读取或修改对话、访问媒体。是否触达管理员权限取决于新身份角色，不在本次已证实范围。
- 限制：未读取现役表结构，不能断言现役 users 表必然与模型声明一致。令牌默认七天有效，攻击窗口受实际有效期和密钥轮换影响。
- 建议：将认证主体绑定不可复用身份或随机令牌版本；一并考虑现有用户迁移、旧令牌失效和 ID 复用。仅修改 ORM 声明不等于已有 SQLite 表完成迁移。
- 验收：在隔离数据库走真实建表/迁移和认证链，完成 A 发令牌→删除 A→创建 B→旧令牌请求，旧令牌必须拒绝；B 自身登录应正常。不要仅用手工构造的不同 UUID 证明问题不存在。

### R02：“不知道”被处理为事实缺口消失

- 位置：backend/agent/controller.py:430–432；backend/agent/writer.py:289、373、865；backend/agent/verifier.py:166–175、329–333。
- 静态证据：显式未知回答只执行 unknown_facts.pop，没有在其他字段保留“已问过、仍未知”；writer 从剩余 unknown_facts 组装输入，missing_information 必须属于仍存在的未知项；verifier 也验证该子集，最终只合并 state unknowns 与 draft missing_information。
- 触发：最后一个关键未知事实被问到，用户回复“不知道”；已有证据足以使后续流程继续。
- 影响：该缺口从后续评估和写作约束中消失，终稿可显示“尚不确定的事实：无”。是否进一步生成具体错误法律结论取决于模型，不能把它写成已动态证实的事实。
- 建议：区分“事实是否已知”和“是否还要追问”，保留未知事实，允许停止重复追问并按条件分析。
- 验收：澄清恢复后，未知事实仍可追溯；不反复追问；writer 可表达该缺口；最终用户文本保留不确定性。只检查 resume 成功或 unknown_facts 变空不能证明修复。

### R03：客户端可控制限流使用的 IP

- 位置：backend/main.py:174–190；Caddyfile:17–19；docker-compose.yml 的 8088:80 映射。
- 静态证据：_rate_key 无条件优先取 CF-Connecting-IP；当前 Caddy 反代配置没有清洗该客户端头。
- 触发：通过可访问的 Caddy 入口发送请求，每次轮换该头；请求映射到不同限流桶。
- 影响：登录、上传、聊天等按 IP 的速率控制可被绕过。是否能经 Cloudflare 的正式入口伪造该头尚未验证；直连入口可达性也需核实现役网络。
- 建议：按可信代理链解析客户端地址，在入口清洗或重建头；登录后业务可增加用户维度控制。保留真实代理后多用户的正常隔离，不要让所有用户共用代理 IP 的一个桶。
- 验收：不可信客户端轮换头不能绕过限制；可信代理路径仍能正确区分用户；测试同时覆盖直连与代理场景。

### R04：登录失败窗口过期后永久绕开锁定分支

- 位置：backend/main.py:395–406。
- 静态证据：失败次数增加，但 ts 始终保留首次失败时间；锁定条件一直比较 now < ts + 300。窗口过期后，即使次数继续增加也不会再次锁定，直到成功登录清除记录。
- 触发：失败达到阈值，等待首次失败后超过 300 秒，再持续输错。
- 建议：明确选择固定/滚动失败窗口或 locked_until，过期后正确重置。使用项目已有时钟与状态机制，避免不必要抽象。
- 验收：用可控时钟测试首次阈值、锁定期间、到期后再次达到阈值、成功清除记录。避免依赖真实等待五分钟。

### R05：会话详情异步响应未校验当前选择

- 位置：frontend/lib/hooks/useConversations.ts:56–82。
- 静态证据：选择时先改 activeId/conversationId，await detail 后无身份校验直接 setMessages；异常分支也直接清消息。newChat 没有使详情请求失效。
- 触发：选择慢响应 A，再选择 B 或新建会话，A 最后返回；若这时开始生成，详情返回还可能替换消息列表。
- 影响：当前会话 ID 与展示内容不一致，后续发送或流更新可能操作错误的视图内容。
- 建议：最小请求序号或等效身份检查，在切换、新建、删除当前会话时失效；成功与失败都要校验。取消请求不能替代迟到结果校验。
- 验收：用可控 Promise 覆盖 A→B 逆序返回、A→新建、旧请求失败晚于新请求成功、详情加载与发送交错。

### R06：文档状态不随会话切换重置

- 位置：frontend/app/chat/page.tsx:45–46、163–177、206–220；frontend/lib/hooks/useConversations.ts:40–83。
- 静态证据：fileInfo/fileContent 未接入会话重置；send 使用 fileContent ?? text，因此残留文档优先于新输入。异步解析完成后也没有视图身份校验。
- 触发：上传文档完成后切换或新建，输入新问题再发送；或解析尚未完成时切换，迟到结果写进新视图。
- 影响：发送错误文档，手输问题被忽略，文档进入错误会话。
- 建议：在会话生命周期内统一重置附件；为文档解析结果增加所属视图校验，可与 R05 共用最小的视图版本机制。
- 验收：分别覆盖解析完成前后切换、新建、删除当前会话；确认发出的文本、附件和 conversation_id 对应正确。

### R07：空摘要被误判为压缩成功

- 位置：backend/memory.py:71–98；生产调用 backend/main.py:1019–1022。
- 静态证据：_extend_summary 在空响应时返回 existing，而 compress 仅把 None 视为失败，随后推进 summary_upto 并 commit。
- 触发示例：message_count=14、summary 为空、summary_upto=0，有未摘要旧消息；模型返回空串或空白。游标可推进到 8，但对应旧消息未被写入摘要。
- 影响：这些消息仍在数据库中，但退出了模型上下文，也不会被后续增量压缩自动补回。不要将其描述为物理删库。
- 建议：空响应返回明确失败信号，保持原摘要和游标。验证类型标注与真实返回约定一致。
- 验收：覆盖空串、空白、异常、正常摘要；失败后再次成功压缩必须仍包含此前遗漏的消息。

### R08：Agent 在整个研究阶段之后才首次检查取消

- 位置：backend/agent/service.py:280、305、335；backend/agent/controller.py:618、634、1002–1035；backend/main.py:855–869。
- 静态证据：连接断开设置取消 Event；service 在分解和完整 controller.run 之后才首次读取；controller 没有取消检查入口，工具循环和 planner 调用间未检查。
- 触发：用户停止、关闭页面或网络断开，发生在分解、检索或规划阶段。
- 影响：取消后仍可能发起新的工具/模型调用，消耗资源；返回停止结果时，持久化状态还可能停留在 DRAFTING 或 WAITING_USER，需独立核查。
- 建议：在阶段边界和每次新调用前检查取消，并按既有状态机约定保存一致状态。取消后不应再发起新工作；已经阻塞中的外部调用能否立即中止须单独说明。
- 验收：可控取消分别发生在分解前、工具之间、planner 前、起草前；检查后续调用计数与数据库状态。区分“不再启动新调用”与“立即打断进行中的调用”。

### R09：Agent 成功调用没有进入配额账

### R10：Service Worker 缓存名只在 install 时恢复

- 位置：frontend/public/sw.js:12、15–34、61、66；frontend/scripts/write-build-id.mjs:6–7。

- 限制：未执行浏览器生命周期复现；缓存混用是否最终造成白屏需另验，不应直接写“必然白屏”。

### R14：浏览器语音识别降级后无法正确停止

- 位置：frontend/lib/hooks/useVoice.ts:18–24、31–40、80–110。
- 静态证据：Web Speech 实例在 recRef；toggleVoice 的 listening 分支只停 wavRecRef，随后直接返回；卸载清理也只处理 WAV。legacyWebSpeech 内虽有 stop 分支，按钮在 listening 时已从外层提前返回，走不到那里。
- 触发：WAV 录音不可用或后端转写失败，进入 Web Speech；再点停止，或离开页面。
- 影响：界面停止状态与实际识别不一致，识别结果可能继续写入输入。
- 建议：统一停止和卸载清理，处理实际活动识别器、定时器与迟到结果；保持正常 WAV 停止后转写行为。
- 验收：两条录音路径分别测试主动停止和卸载；停止后无新增识别回填；重复开始/停止不留下多实例。

## 4. 建议实施顺序与简化原则

1. 先确认目标工作树、既有授权及未提交修改，再独立确认 R01、R02。
2. 安全控制一起核查 R03/R04；它们可能组合削弱登录防护，但应分别提供证据。
3. 会话状态一起处理 R05/R06；可共用最小的视图身份机制，不必建设通用异步任务框架。
4. R07 单独修复摘要失败约定，避免与大规模 memory 重构捆绑。
5. Agent 的 R08/R09 各自检查状态与记账契约，尤其不要以移除预算、关闭校验或静默 fallback 解决问题。
6. 运维的 R11/R12 一起验证“备份正确对象→副本恢复验证→失败状态可观察”。
7. R10 需要生产 Worker 生命周期验证；R13/R14 可以各自最小修复。

采用 Ponytail 简化阶梯：先判断是否需要新增机制，再找库内已有能力、标准库、平台原生能力、已装依赖，最后才做最小实现。**简化不能削减输入校验、身份边界、数据保护、无障碍或用户显式要求。**本次没有发现足以单独立项的大规模架构替换理由，也没有测量可删除行数或收益。

可选补查，不纳入上述 14 项确认范围：backend/main.py 的上传 async 路由（约 1507、2953 行）同步调用文档解析；复杂合法 PDF/DOCX 可能阻塞事件循环。需核对最终执行上下文和线程池边界，并在隔离输入下验证；不得把未经测量的阻塞时长写入结论。
