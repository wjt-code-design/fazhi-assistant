### A6-01：额外核对了写作调用边界

`backend/agent/runtime.py:486` 的双向包含判定仍接受“工资/工作/合同”覆盖完整分句；`:549` 附近的分解器默认启用事实修复，本次没有为了复现而关闭它。

重新运行结果：

- 短词案例：`non_verbatim=[]`、`uncovered=[]`，decomposer 调用 1 次；Writer 投影不含 `8000`、`三年`、`没有签订`。
- 完整分句对照：同样通过来源检查，上述三项均在 Writer 投影中。
- 原问题仍完整保存在 state。

为排除“模型实际还会收到原问题”的可能，另读了 `backend/agent/writer.py:840` 与 `backend/agent/runtime.py:888`：generator 接收 payload 和固定 system prompt，HumanMessage 序列化该 payload；没有在此拼入 state.user_question。因此写作投影缺口的判断有调用方支撑。

**限定：** 本次并未让该合成状态走完真实检索、控制器、Writer 模型和 verifier。不能声称该输入必然形成并发布错误法律答案。应修复的是确定性覆盖判定和输入完整性。

### A6-02：将“完成后”明确为本次 service 返回后

当前 `backend/main.py:1930 → :1962`、`:2022 → :2034` 顺序未变，`chat_integration.py:78` 序列化已得到的结果。

原报告“Agent 完成后才开始 SSE”应理解为：**本次 service 返回完成、澄清或失败等结果之后，才建立该 Agent SSE 响应**。并非整个跨多轮澄清的会话必须最终结案后才会响应。发生 fallback 时则转入普通链路，不能把后续输出继续算作 Agent 正文。

虚拟计时器复跑结果：阈值 180000ms，fetch_aborted=True，错误为“连接超时，已中断”，promise 返回，计时器清理。没有真实等待 180 秒。

### A6-03：重新验证取消回调的调用顺序

`backend/agent/service.py:280` 的分解、`:305` 的 controller.run 仍在 `:335` 首次取消检查之前。实际 service 接入始终为 True 的取消回调，再次得到：
