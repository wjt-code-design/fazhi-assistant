# 查询改写原型 · 实验结论（2026-10-25）

**结论：暂不接入生产。** 改写能把部分口语问句救回，但净收益不稳定（修 6 破 4），
且同一题两次运行会生成不同改写词（temperature=0 仍未完全确定），无法作为稳定链路。

## 实验设计

对 `data/eval_set_gen_all.json` 的 59 题，比较三种检索：

| 变体 | 做法 |
|---|---|
| orig | 原问句直接检索（现有生产行为） |
| rewrite | LLM 把口语问句改写成「事实 + 法律术语」查询后检索 |
| fuse / rerank_union | 原问与改写各取 k=6，RRF 融合 / 并集后按原问 rerank |

改写模型：text 档旗舰（`_judge.pick_text_llm()`，temperature=0）。
脚本：`backend/scripts/proto_query_rewrite.py`（纯实验，未接生产）。

## 结果

### 5 个检索失败样例（首轮）

| id | 原问 rank | 改写后 rank | 是否救回 recall@4 |
|---|---|---|---|
| 101 赠与撤销 | 未命中 | 4 | 是 |
| 103 刑诉二审裁定 | 未命中 | 未命中 | 否 |
| 108 保险负责人处罚 | 未命中 | 6 | 否（仅进 k=6） |
| 113 破产重整担保权 | 未命中 | 1 | 是 |
| 117 询问证人 | 5 | 2 | 是 |

### 全量 59 题

| 变体 | recall@4 | 变化 |
|---|---|---|
| orig（基线） | 50/59 = **0.8475** | — |
| rewrite | 52/59 = **0.8814** | +2 净增 |

- 救回 6 题：108、113、117、133、140、141
- 反而丢失 4 题：116（2→9）、129（1→6）、137（2→None）、152（1→7）

### 稳定性复测（13 个边界题重复跑）

同一批题第二次运行，改写词与首轮不同，结果也不同：

- 108：首轮改写命中 rank 1，复测未命中
- 113：首轮 1，复测未命中
- 129：首轮 6，复测 未命中

说明改写环节本身不可复现。RRF 融合复测 7/13 命中，但并集 + 原问 rerank
（`rerank_union`）没有救回任何新题，等于退回原排序。

## 为什么不能直接上线

1. **不可复现**：同样输入、temperature=0，改写文本仍会漂移，指标无法稳定归因。
2. **无门控**：改写对 4 题有害；生产无法预知哪些题该改写。
3. **成本**：每题多一次 LLM 调用 + 一次检索，59 题实测明显变慢。

## 如果继续做，正确的路线

1. **确定性改写**：不用自由生成，改用「术语词典 + 模板」（如「送东西反悔」→
   追加「赠与 撤销」），可复现、可审计。
2. **按检索分数门控**：只在首轮 rerank 最高分低于阈值时触发改写，避免伤到已命中的题。
3. **缓存改写结果**：同一问句复用，避免重复调用。

以上均未实施，等第三方金标复核后再排期。
