# 语料时效数据票：可行性实测 + 备料与待签字清单（2026-09-25）

性质：**取数与判断分离**的第一步交付物。本轮**不写任何库**（真实 `chroma_db` 被运行中的
`fazhi-backend` 容器 bind mount，且 Owner 裁"本轮不动库"），只回答两件事：
① 外部法源到底给不给得出本仓谓词需要的那三个字段；② 给不出的那部分，需要谁签字定什么。

上游依据：`docs/auth-review-followup-guidance-20260924.md` §3（AUTH-B 改判为"先补语料"）与
`docs/progress-auth-review-20260924.md` 第 10 节③（生效语料**没有日期轴**：10266 条 chunk 的
`status` 全为"现行"、`effective_from` / `effective_to` 全空 ⇒ R15-3 的历史法覆盖率 = 0）。

## 1. 实测读数：外部源能给出什么

取的是**元数据形状**，不是某一部法的完备性。两条真实调用（工具：`yuandian_legal_data`）：

| 本仓需要的字段 | 外部源的字段 | 读数 |
|---|---|---|
| `status` | `validity_status` | **给**："失效" / "现行有效" 二值（合同法、合同法解释一/二均为"失效"） |
| `effective_from` | `effective_date` | **给**：ISO 施行日（合同法 `1999-10-01`；解释（二）`2009-05-13`） |
| **`effective_to`** | —— | **不给**。两个接口都没有"失效日期/废止日期"字段，只有二值状态 |
| 逐条正文（切 chunk 用） | `content` | **给**：一次调用返回**全文含章、节、条号与条文**（合同法 428 条全文，附则第 428 条写"本法自 1999 年 10 月 1 日起施行，三部旧合同法同时废止"） |
| 溯源 | `id` / `url` / `document_number` / `issuing_authority` / `publication_date` / `primary_effect_level` | **给**：可支撑"每条 chunk 带外部 id + 文号 + 取数日"的可复核形状 |

两个附带事实，会影响票面设计：

- **`publication_date` ≠ `effective_date` 是常态**（合同法：公布 1999-03-15 / 施行 1999-10-01）。
  本仓若把"衔接日"取错这一列，跨施行日的合同/侵权事实的版本判定就会整体偏移。
- **取数通道不能走 agent 上下文**：两次调用各返回 3–5 万 token 的全文。批量备料必须是
  **脚本直连接口落盘**，而仓库内现在**没有任何外部法源客户端**（`backend/**/*.py` 里
  `chineselaw|yuandian|ydzk|flk|openlaw` 零命中）⇒ 凭据与取数方式是一条需要定的口径（见 §3-D）。

未验（且本轮不该再花一次全文调用去验）：`reference_date` 声称能"查询指定日期有效的版本"。
若为真，它是**唯一**有可能直接给出历史有效性的入口 ⇒ 列为本票第 2 步（用小接口
`yuandian_search_laws_and_regulations` 对同一部法取两个 `reference_date` 比字段差异即可，不必拉全文）。

## 2. 为什么 `effective_to` 是承重的、而不是可选的

`retrieval_core.is_valid_by_time` 是全仓**唯一**的日期谓词（向量池 / BM25 / grounded 打分三处共用），
它的 fail-closed 分支写死了这件事：

```python
if status == "已废止" and not et:
    return False  # 无法证明在查询日仍有效
```

⇒ 如果只导入"合同法=已废止"而 `effective_to` 留空，结果是**所有**查询（含历史查询）一律取不到它，
比现在"根本没有历史法"更糟：看上去补了语料，实际一个召回都不变，还会被误读成"补过了"。
这条就是本票第 2 节要报给 Owner 的**主结论**：`effective_to` 拿不到 ⇒ 整个导入必须等签字，
不能用"先导入现行部分"的方式分批上线。

另有一条同源风险：`scripts/backfill_time_meta.py:19` 的默认值是
`{"status": "现行", "effective_from": "", "effective_to": ""}`。存量 10266 条就是这个形状
⇒ 它们在新谓词下等价于"无限制、永远有效"。补历史法时若不动这批默认值，
"1999 年的合同法"与"2021 年的民法典"会同时命中同一问题，版本冲突由谁负责就变成随机。

## 3. 待签字清单（判断归 Owner / 法务，取数归执行助手）

| # | 要定的事 | 我的推荐与依据 | 不签的后果 |
|---|---|---|---|
| A | `validity_status` → 本仓 `status` 词表的映射 | "现行有效"→`现行`、"失效"→`已废止`。依据：谓词只认 `已废止` / `即将施行` / `未生效` 三个字面值，其余值按"无管理状态"处理 | 词表写歪 ⇒ fail-closed 分支不触发，等于没有闸 |
| B | **废止日 `effective_to` 的取法**：取"替代法施行日"还是"废止决定的公布日" | 推荐**替代法施行日**（合同法 → `2021-01-01`；依据是《民法典》第 1260 条同时废止包括合同法在内的一批旧法并于当日施行——**条号与废止清单我未取原文核对**，签字前需按源文本复量）。该口径与 R15 版本门用的 `CIVIL_CODE_EFFECTIVE = 2021-01-01` 同源，不新立分水岭 | 两种口径对多数法是同日，但**对司法解释不是**（下面 C 条）⇒ 不定就每人各写一种 |
| C | **被批量废止的司法解释**用哪个文号/日期 | 合同法解释（一）（二）在源里状态"失效"但无日期。推荐按最高人民法院 2020 年底清理司法解释的那批决定取**施行日**（与 B 条同口径）；⚠️ 具体文号（我印象是法释〔2020〕16 号一类）与公布/施行日**都未从源取到**，属"先验知识，需核对"，不代签 | 解释类文本正是"时效衔接"最常被引的一层，缺日期就进不了库 |
| D | **取数通道与凭据**：脚本直连（凭据从哪读、是否进 `.env`）还是人工导出后由脚本切片 | 推荐脚本直连 + 凭据只进 `.env`（本仓纪律：按值反查扫密、禁提路径零命中）；产物落 `dispatch-output/` 之类的未跟踪目录，**入库前只做只读校验** | 没有这一条，票面第一步就无法执行；走 agent 上下文取数会把全文灌进会话（已实测代价） |
| E | **是否引入《民法典时间效力若干规定》（法释〔2020〕15 号）作为衔接依据** | 推荐**引入文本、暂不改判定语义**。R15 的版本门现在是单一分水岭日期比较；该规定含"跨 2021-01-01 的持续性法律事实适用新法"这类规则，一旦作为判定输入就是**改语义**，需单独开票 + 单独判据 | 不引入则门只能答"两边法不同"；引入而不签字则门会静默改判据 |
| F | 每条 chunk 的溯源键放哪 | 推荐沿用 `extra_meta` 透传（上传路径已支持 `status`/`effective_from`/`effective_to` 三键），另加 `source_doc_id` + `source_url` + `retrieved_at` 三键；**新键要不要进时效白名单**由 Owner 定 | 无溯源 ⇒ `qa_provenance_verifiable` 那类"来源可校验"判据在 provision 侧没有对应物 |

## 4. 备料清单（按语料缺口排序，字段留空待签）

只列**能直接改变现有评测读数**的最小集合。`effective_to` 一列在签字前一律留空——
按 §2 的机制，留空就是拒，不会误放行。

⚠️ **日期列分两种来源，别混着读**：标"已实测"的是本票 §1 那两次调用从源里读到的值；
标"**待源确认**"的是我（执行助手）的先验知识，**本轮没有从外部源取到**，
不得当作入库依据——通道（§3-D）定了以后由脚本逐行取回替换。这正是本票第 3 条纪律的样子：
凡"事实"必须带着它是怎么来的。
