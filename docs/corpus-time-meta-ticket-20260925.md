## 1. 实测读数：外部源能给出什么

> **2026-09-25 本节重写**。第一版只有两次调用（法级详情 + 检索列表）就把 `validity_status` 读成
> "二值"，那是**覆盖面不足**而不是接口形状：本轮按 Owner 裁定的工作源（元典 MCP）跑了 20 次调用，
> **法级 7 部全覆盖**、**条级取到其中 6 部**（缺《民法典时间效力若干规定》的条级，本轮只到法级），
> 字段清单与取值集合都以当次响应为准。

取的是**元数据形状**，不是某一部法的完备性。工具：`yuandian_legal_data` 的
`..._search_laws_and_regulations`（法级）与 `..._search_legal_articles`（条级）。

| 本仓需要的字段 | 外部源的字段 | 读数（本轮口径：两个接口的返回字段全集） |
|---|---|---|
| `status` | `validity_status` | **给**，且是**五值**词表：`现行有效` / `失效` / `已被修改` / `部分失效` / `尚未生效`。本轮**实测到 3 值**（`现行有效`、`失效`、`已被修改`），`部分失效` / `尚未生效` 这轮**没有观测到实例** ⇒ 映射表按五值写，但只有三个值有实测支撑 |
| `effective_from` | `effective_date` | **给**：ISO 施行日（合同法 `1999-10-01`、民法总则 `2017-10-01`、解释（一）`1999-12-29`） |
| **`effective_to`** | —— | **不给**。法级列表、法级详情、条级三层的字段集里都没有"废止日期/失效日期"这一列，只有五值状态。三层的字段全集见 §1b |

### 1b. "给不出废止日期"这一条现在的取证面（比第一版宽）

**先把取证面分清，别把三层的读数说成同一轮取的**：

- 本轮实际调用的是**两个**接口：法级检索（`..._search_laws_and_regulations`）与条级检索
  （`..._search_legal_articles`）。它们当次响应里出现的键，逐次一致：
  - 法级：`id, url, title, region, regulation_name, validity_status, effective_date,
    publication_date, document_number, issuing_authority, primary_effect_level,
    secondary_effect_level, _score`
  - 条级：以上 + `article_id, article_number, number, content, llm_content, regulation_id`
- **第三层（法级详情 `..._get_law_or_regulation_detail`）本轮没有再调**——它一次返回整部全文
  （3–5 万 token），"有没有废止日这一列"在 09-25 早段那一次全文调用里已经读过：**同样没有**。
  ⇒ 所以"三层都给不出废止日"这句话里，两层是本轮逐次记录、一层是同日早段的读数；不重取是成本决定，
  不是"推定它也没有"。
- 三层都没有任何一列形如 `repeal_date` / `invalid_date` / `stop_date` / `废止日期`。

⇒ 结论不变但依据换了：**废止日不在接口输出里**，只能在"替代法/废止决定的施行日"上重建（§3-B）。

### 1c. `reference_date`：在实测过的调用形状下**不切换**（不是"接口没有该能力"）

第一版写的是"未验"。本轮实测：对**同一部**合同法第 129 条，带 `reference_date=2020-06-01`
（彼时合同法尚未废止）与不带该参数取数，返回的是**同一条记录、同一个 `id`、同一个
`validity_status=失效`**。⇒ 至少在该调用形状下，`reference_date` 没有把状态切回当时的有效性。
措辞要收紧：这证的是"**该形状下不切换**"，不证"元典没有历史版本能力"——它可能要靠
"同名法的多版记录"来表达（见 §1d 的民法通则）。因此本票**不**把它列为可直接取废止日的入口。

### 1d. 外部源把"被修改"表达成**多条同名记录**，不是在一部法上加一列

实测：`中华人民共和国民法通则` 在源里是**两条**——`(2009修正)`（施行 `2009-08-27`，失效）与
原文（施行 `1987-01-01`，失效），两条都 `validity_status=失效`；同族的 `劳动合同法` 则是
原文 `已被修改`（施行 `2008-01-01`）+ `(2012修正)` `现行有效`，另有
`关于修改…的决定(2012)` 一条，其 `secondary_effect_level` = `修改、废止的决定`。
⇒ 本仓要的是"一条 chunk 一个有效区间"，而源给的是"版本各成一部法"——
**选哪一版**（1987 原文还是 2009 修正文本）是**衔接口径判断**，不是取数结果，归 §3 签字。
本轮按签字口径"只下发条级一致的两类"，多版法**一律先不下发**。

### 1e. 给下一步脚本的取数形状读数（每条都是本轮踩过才知道的）

1. **条号 / 长原句做关键词命中不了，短正文特征词能命中**（但这条读数**有两个变量同时变**：
   `regulation_name` 过滤器一直在场）：`keyword="第一千二百六十条"` 与
   `keyword="本法颁布前的民事关系"` 都返回"未查询到相关数据"，而 `keyword="同时废止"` 直接命中
   民法典第 1260 条 ⇒ 批量取条要按**短正文特征词**或 `?text=<条号>` 深链走；
   脚本阶段第一件事是**单变量复量**（去掉过滤只留条号）才能把"关键词形状"与"过滤形状"分开。
2. **条级接口的 `regulation_name` 是"标题命中即返回"，不是精确所属法规过滤**：用
   `regulation_name="民法总则"` 过滤时，返回里有《北京市高院关于〈民法总则〉…参考意见》和
   《最高法关于适用〈民法总则〉诉讼时效制度若干问题的解释》⇒ 脚本必须按 **`regulation_id` 二次过滤**。
3. **文号括号全半角混用**：`法释[1999]19号`、`法释[2009]5号`（半角）与 `法释〔2020〕15号`、

4. **正文带编辑性标记与结构残词**：合同法第 129 条 `content` 末尾挂着 `分则`，民法通则 135 条原文带
   `【普通诉讼时效】` 而 2009 修正版同条不带 ⇒ 入库前必须过本仓 `scripts/clean_law_text.py` 并复量，
   否则这些标记会进 chunk、进引用、进评测。
5. **取数通道**：本轮全部走**已授权的元典 MCP**；脚本对 `flk.npc.gov.cn`（Owner 指定的法源站点）出网
   那条请求被权限层拦下，按纪律**不重试**——它是 Owner 需要单独放行的动作，不是我该绕的墙。

## 2. 为什么 `effective_to` 是承重的、而不是可选的

`retrieval_core.is_valid_by_time` 是全仓**唯一**的日期谓词（向量池 / BM25 / grounded 打分三处共用），
它的 fail-closed 分支写死了这件事：

```python
if status == "已废止" and not et:
    return False  # 无法证明在查询日仍有效
```

⇒ 如果只导入"合同法=已废止"而 `effective_to` 留空，结果是**所有**查询（含历史查询）一律取不到它，
比现在"根本没有历史法"更糟：看上去补了语料，实际一个召回都不变，还会被误读成"补过了"。
这条就是本票第 2 节要报给 Owner 的**主结论**：`effective_to` 拿不到 ⇒ 整个导入必须等签字，
不能用"先导入现行部分"的方式分批上线。

另有一条同源风险：`scripts/backfill_time_meta.py:19` 的默认值是
`{"status": "现行", "effective_from": "", "effective_to": ""}`。存量 10266 条就是这个形状
⇒ 它们在新谓词下等价于"无限制、永远有效"。补历史法时若不动这批默认值，
"1999 年的合同法"与"2021 年的民法典"会同时命中同一问题，版本冲突由谁负责就变成随机。

**本轮把这条风险从"假设"升级成"有实测形状"**：`is_valid_by_time` 的 fail-closed 只认
`已废止`/`即将施行`/`未生效` 三个字面值（`retrieval_core.py:58-61`），而本仓词表里还有一个
`已修改`（`:38`）——**它不在任何拦截分支里**。所以"被修正版替代的旧版"若只标 `已修改` 不补
`effective_to`，它在任何查询日都算有效，与新版**同时**命中。外部源确实把版本各存成一条记录
（劳动合同法 2008 版 `已被修改` + `(2012修正)` `现行有效`，§1d）⇒ 这一格已写进 §3-A 请法务签字，
不是脚本可以自行拍板的格式问题。

## 6. 顺带查出来的两条代码侧事实（本票不改，只记）

1. **两个钟**：`retrieval.exact_article_lookup`（`retrieval.py:379`）的默认基准日是
   `date.today()`（**本地**钟），而票 AUTH-A-2 的写侧 `add_qa_pair` 落 `law_as_of_basis` 用的是 **UTC**
   （为与 `QaCandidate.created_at` 的 `datetime.utcnow` 同钟，见 `knowledge_service.py`）。
   ⇒ 跨本地午夜那一刻两者最多差一天。对本次的分水岭判定不敏感（差一天不会跨过 `2021-01-01`），
   但对"**即将施行**"的条文是真差一天：`is_valid_by_time` 的 `ef > today` 分支（`retrieval_core.py:54`）
   会在本地日与 UTC 日之间给出不同答案。**要统一到哪一把钟是口径判断**，不在语料数据票范围内，
   也不该由执行助手顺手改判据。
2. **本仓状态词表本来就是五值**：`retrieval_core.py:38` 的 `STATUS_WHITELIST` 含 `已修改`，
   而 `is_valid_by_time` 的 fail-closed 分支不覆盖它（§2 末）。⇒ 导入历史法时"给 `已修改` 补
   `effective_to`"这一句必须写进签字口径，否则补了语料反而制造双版本同时命中。
