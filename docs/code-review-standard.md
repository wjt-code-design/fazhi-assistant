# 代码审查标准与流程 —— 法智（ai-legal-helper）

> 版本：v1（2026-09-10 制定）　适用范围：**本仓库当前的实际工作方式（脏工作树 + 哈希锚定 + 付费验证轮）**
> 定位：本文是**可执行的审查标准**，不是风格散文。每一条 🔴 都由**机器或一条命令**可判定。

## §1 依据：现状实测（先测量后定标准）

### 1.1 现有 CI 四道门禁的实测结果（2026-09-10，`working-directory: backend`）

| CI 门禁 | 命令 | 实测 | 判定 |
|---|---|---|---|
| ruff lint | `ruff check .` | **77 errors**（W292×24 / F401×14 / I001×10 / E402×8 / F541×5 / E731×4 / E702×3 / F841×3 / UP017×2 / B007 / B011 / UP012 / UP037） | ❌ 红 |

**关键事实：这套门禁由 `.github/workflows/ci.yml` 在 `push`/`pull_request` 触发，而本仓库的事实工作方式是「不提交、不建 PR、用哈希锚定候选」**（HEAD 长期停在 `ebe82e2`，T0–T8 全部工作在脏工作树里）。⇒ **CI 从未在这批改动上跑过；一跑就是三道红。**

> 另有环境事实：`pytest --cov` 在本机默认**跑不起来**（safe-delete 沙箱拦截 coverage 擦除 `.coverage` → `SHFileOperationW 失败: 0x2`）。绕行：`CODEBUDDY_SAFE_DELETE_ENABLED=0`。**这条要写进标准**，否则"cov ≥70 通过"无法在本机验证。

### 1.1b 同日晚修复后的终态（19:15–19:50）

按"先让门禁真的产出信号"的顺序修复，结果：

| 门禁 | 修前 | 修后 |
|---|---|---|
| `ruff check .` | ❌ 77 errors | ✅ **All checks passed!** |
| `ruff format --check .` | ❌ 135 文件 | ✅ **204 files already formatted** |
| `mypy .` | ❌ 配置错误中止（零覆盖） | ✅ **Success: no issues found in 63 source files** |
| `pytest`（全量） | ✅ | ✅ **918 passed / 0 failed** |

修复内容（**每条都留痕，不是静默放宽**）：

1. **mypy 配置**：原 `exclude = ["tests/"]` 用 mypy 的 `re.match` 语义匹配不到子路径，且 `backend/`、`scripts/` 均无 `__init__.py` ⇒ 同一文件被映射两次。改为 `mypy_path="."` + `explicit_package_bases=true` + 能匹配整路径的 exclude，并补排 `venv/`（首次修好后 mypy 连 venv 都在检查）。
2. **冻结物处理**：`verifier.py` 的唯一报错是 `var-annotated`（修它就要改冻结物）⇒ 用**最窄的单条错误码 override** 放行，并注明"unfreeze 时必须删掉本 override"。ruff 侧则把 6 个冻结文件整体排除（名单与 frozen 哈希锚定一致）。
3. **真代码缺陷（mypy 首次跑出来）**：
   - `controller.py` 的 `while True:` 里有一个 `break`，而**循环之后函数已无任何代码** ⇒ 该路径会**隐式返回 `None`**（调用方期望 `ControllerResult`）；注释写的"出循环交状态分派"**从未实现**。按可达性分析该路径当前不可达，但无任何保护 ⇒ 改为**显式 fail-closed 的 AssertionError**（service 会折叠为带栈的 `AGENT_EXECUTION_FAILURE`）。**这是启用门禁后抓到的第一处真缺陷。**
   - `DraftGenerator.generate` 与 `Planner.decide` 两个 **Protocol 落后于实现**：`71e5f23`（错误回喂）给实现加了 `feedback` 关键字，协议没跟着改 ⇒ 新实现照协议写会在回喂路径炸。已补齐。
   - `_find_pending_unknown` 注解过宽（`state: object` / `-> tuple[str, object]`）⇒ 收紧为真实类型。
4. **ruff 的 19 处非自动可修**：8 处 E402 是设计使然（`auth.py` 的 UTC 兼容 shim、`mcp_server.py` 的 `load_dotenv`）⇒ 加 **per-file-ignore 并注明理由**；其余 11 处是真问题（未用变量、λ 赋值、一行多语句、`assert False`）⇒ **改代码**，不是加忽略。

**代价（必须如实记）**：`ruff format` 重排 **133 个文件**，候选因此从 **18 个文件膨胀到 137 个**（备份 patch 9153 行 / 425 KB）。
⇒ **这是一次性的机械债清理**；此后新改动应保持 `ruff format` 绿，候选不应再出现这种量级的膨胀。
**安全性已验证**：冻结物逐文件哈希**漂移 0**（格式化确实没碰它们）；全量 918 passed 证明行为未变。

## §2 分级与阻断规则

三级。**🔴 的每一条都是可枚举、可机器或可复算判定的**——不写"严重问题必须修"这类形容词条款（那等于没写：谁都能说自己的问题不严重）。

### 🔴 阻断（候选不得冻结、付费轮不得开跑）

| ID | 条目 | 怎么判定 |
|---|---|---|
| B1 | 触碰冻结物（`verifier` / `chat_integration` / `state_machine` / `repository` / `prompts` / `gate5_judge` / `frozen-*` / `hidden-*` / 历史 sessions） | 冻结物哈希复算，漂移非零 |
| B2 | 报告中的数字**无法用一条命令复现**（口径不明／跑不出来／引用的旧输出） | 命令可复算；口径须写明 |
| B3 | 新增测试**没有 watch-it-fail 证据**（不知道自己测对的是不是对的东西） | 提供"为正确原因红过"的留痕或等价代理 |
| B4 | 测试期望值**与实现同源**（复算实现，而非独立来源） | 期望必须来自独立来源（手算/已知条文/更早的独立采集） |
| B5 | 日志/诊断字段**会被静默丢弃**（不在 `observability._ACCOUNT_FIELDS`） | `tests/test_log_field_whitelist.py`（AST 哨兵）自动判定 |
| B6 | 破坏"**预登记 = 执行条件唯一来源**"（同轮混用不同代码状态／改了条件不重登记） | manifest ↔ 工作树 ↔ run 三方一致 |
| B7 | 循环/重试/补齐**没有终止条件**（写的是"是否已达成"而不是"是否已尝试"） | 代码评审 + **必须实测"外部依赖持续无产出"边界** |
| B8 | 独立复核**未做**且无显式豁免留痕 | §3 流程 |
| B9 | `ruff check .` / `ruff format --check .` / `mypy .` 未绿 | 三条命令的退出码 |

### 🟡 应修（记录并排期，不阻断）
可诊断性缺失（失败无详情、不可复算）；契约边界模糊（同一判定在多处复刻）；**未做边界实测**（只测正常路径）；命名/结构误导；缺少"这一条为什么这么写"的证据注释。

### 💭 建议
风格、重复、格式（工具能管的交给工具）。

### 豁免
Owner 可豁免**任意**条目，但**必须在决策留痕里写明理由与影响**。
理由：§5.5 那种"隐性跳过"比"显式豁免"危险得多——显式豁免至少留下判断痕迹，可被后人追责/复盘。

## §3 审查流程（两个关卡）

本仓库没有提交点，所以关卡设在**两个真实动作**上：

### 关卡 1 · 候选建立（重采锚定）
1. 实现者**自审**：附 §4 的检查清单结果 + 每条 🔴 的处置。
2. 冻结物哈希复算；全量 `pytest tests/`（**本次运行**，junit 取机器可读计数）。
3. `ruff check` / `ruff format --check` / `mypy`（§2 B9）。
4. 重采候选锚定 + 生成可还原备份（patch），并做**防漏**：新增的 tracked 脏文件**与**未跟踪新源码都要纳入。
5. **独立复核**（§3.1）→ 通过才允许冻结。

### 关卡 2 · 付费轮开跑前
1. **预登记**：把本轮判据写死（且每条判据必须能**区分"好结果"与"没生效"**——这是 §12.11 的教训）。
2. 执行条件核对：模型 / 题集 / 端口 / 环境变量与预登记**逐项一致**；服务**重启**（源码改动晚于进程启动视为必须重启）。
3. 前置哨兵（例：`/healthz` 三真、`admin/stats` 的模型名、非付费的 `AGENT_ENABLED` 判定）。
4. 跑完后：逐题留证（sessions + DB + 日志）+ 两层 judge；**未跑完的轮次标 PARTIAL，不得换分母**。

### 3.1 "独立复核"的定义（这一条必须写死）
- **实现者不得担任复核者。**
- 可接受的替代性独立：**不同会话 + 不共享实现者的中间结论 + 从原始证据（DB / sessions / 留痕文件）重算**。
- 必须在该轮记录里**显式标注它与真第三方的差距**（例如"同一工具链、同一仓库"），防止被冒充为完整独立验收。

## §4 检查清单（按关卡勾选）

**关卡 1（候选建立）**
- [ ] 改动面清单（tracked 脏文件 + 未跟踪源码）已枚举，且锚定脚本的**防漏检测**（新增脏文件 / 未跟踪新源码）为 0 遗漏
- [ ] 冻结物哈希：漂移 0
- [ ] 全量 `pytest`：本次运行 0 failed（junit 口径；退出码被 safe-delete 污染，不可信）
- [ ] `ruff check` / `ruff format --check` / `mypy` 三绿
- [ ] 新增测试有 watch-it-fail 证据；期望值独立来源（§2 B3/B4）
- [ ] 循环/重试有终止条件，且**"外部依赖持续无产出"边界已实测**（§2 B7）
- [ ] 新日志字段已登记白名单（AST 哨兵绿）（§2 B5）
- [ ] 注释/报告里的每个数字都能指到一条命令或一个留痕文件（§2 B2）
- [ ] 独立复核完成，或豁免已留痕（§2 B8）
- [ ] 已知限制已显式写出（哪些没做、哪些只在什么条件下成立）

**关卡 2（付费轮前）**
- [ ] 预登记判据**可区分"好结果"与"没生效"**
- [ ] 服务已重启且启动时刻晚于源码改动
- [ ] 前置哨兵通过
- [ ] 执行条件与预登记逐项一致（模型/题集/端口/预算）
- [ ] 失败与 unknown 题原样保留；unknown 未经人工确认不重跑

## §5 可执行检查的落地

原则：**能写成无参测试的，一律写进 `backend/tests/`**——因为团队已经习惯在关卡 1 跑 `pytest tests/`，这样标准**自动搭上现有习惯的顺风车**，不依赖任何人记得跑。

| 检查 | 形态 | 现状 |
|---|---|---|
| 日志字段白名单哨兵（§2 B5） | pytest（AST 静态扫描 + 自带 watch-it-fail） | ✅ 已实现 `tests/test_log_field_whitelist.py` |
| 预算装得下契约允许的最大分解（§1.2 #8） | pytest | ✅ 已实现 `test_budgets_fit_contract_max_decomposition_and_never_narrow` |
| 事实缺陷修复环终止性（§2 B7） | pytest（缺口持续不改善必须严格有界） | ✅ 已实现 |
| 修复不劣化（Pareto 采纳规则） | pytest | ✅ 已实现 |
| 候选锚定一致性 + 防漏（§2 B6） | CLI 门禁（需外部输入：manifest 路径） | ✅ 脚本已具备；**待加退出码语义** |
| 对照脚本口径自检（UUID 排序 / DATETIME 亲和性 / 窗口上界） | CLI / 脚本内断言 | ⚠️ 今天刚踩过，**待固化** |
| 判据鉴别力自检（§3 关卡 2） | 评审清单（暂无法自动化） | ⏳ |

**CLI 门禁约定**：退出码 0 = 通过；非 0 = 阻断，并在 stdout 打印"哪一条 🔴 失败 + 复算命令"。

## §6 与既有资产的关系

- 本标准**不替代** `CONTRIBUTING.md`：后者的规则（法律文本零改动、domain_rules 单一来源、期望值独立来源、测试命名即规格、禁提交 .env/密钥/用户数据）**全部继续有效**，本文把它们升格为 🔴/🟡 条目。
- `.pre-commit-config.yaml` 与 `.github/workflows/ci.yml` **保留**（将来若恢复提交/PR 流程即可用），但**不作为本仓库当前的主门禁**——主门禁是本文 §3 的两个关卡。
- 本文与 `docs/handoff-*.md` 的关系：handoff 是**过程与决策留痕**；本文是**判定标准**。冲突时以本文的条目为准，但条目本身若与执行书冲突，须走 §2 豁免流程。

## §7 自审：本标准的已知局限

1. **§1.2 的"命中 0/9"只覆盖今天暴露的缺陷类型**，不是对全体缺陷类型的完备枚举。
2. **🔴 条目可枚举，但枚举必然不完备**——新缺陷类型出现时要按 §3 的豁免/新增流程补条目（今天的 5 处日志字段丢弃，就是被"新条目"抓出来的）。
3. `mypy` 的配置错误（§1.1）修好后，**类型检查才真正开始产出信号**，其误报率未知，可能需要在 `[tool.mypy]` 里加 override——这件事本身要留痕，不能静默放宽。
4. 独立复核的"替代性独立"与真第三方**仍有差距**（§3.1），本标准不假装它等价。
