## A1. 失败持久化必须显式返回保存结果（最高实现优先级）

问题入口：`backend/agent/service.py::_persist_drafting_failure`。

当前函数只返回 int，无法区分保存成功、CAS 冲突和数据库故障。修改目标是让调用方能够诚实报告持久化结果，且保留原业务失败供诊断。

### 推荐的最小实现

优先让 helper 保存成功返回新版本，保存失败向上抛已有 `RunVersionConflict` 或存储异常；在一个共享调用点统一映射公开结果。若现有多个分支用小型结果类型更清楚，也可用包含 outcome/version 的 NamedTuple。两种方式选一种，不同时增加异常封装层和结果封装层。

| 保存结果 | 公开 reason_code | 状态/写入规则 |
|---|---|---|
| 成功保存 FAILED | 原业务 reason_code | 返回新版本；AgentStep 保留业务阶段 |
| CAS 冲突 | `AGENT_FINALIZATION_CONFLICT` | 不覆盖新状态，不追加重写或 fallback |
| 数据库存储故障 | `AGENT_STORAGE_FAILURE` | 不宣称 FAILED 已持久化，不追加外呼 |

原业务码不能只塞进写失败的数据库记录：存储故障时记录脱敏日志，包含 run_id、失败阶段、原业务码、保存错误类别。不要记录用户全文、模型原文、异常中可能包含的 SQL 参数或凭据。若日志字段有白名单，同步检查实际 formatter 能输出它。

调用方已有的断连、终稿 CAS 冲突和尚未创建 run 的错误保持各自契约；不把所有异常转为 FAILED。返回冲突时不伪造“最新版本”，也不重新加载赢家版本后覆盖。

### 红测试先于代码

修正 `test_failure_persistence_storage_error_keeps_original_reason` 的期待：原实现必须因返回业务码而红，新实现应返回 storage failure。另覆盖 CAS 冲突，最好两个真实 Session 或按真实 CAS 更新制造版本变化；仅 mock 抛异常可验证映射，但不能替代数据库并发语义验证。

至少验收：

- writer 初次失败后 FAILED 保存失败：storage failure、无终稿、零追加外呼。
- coverage attempt 已保存，重写失败，再保存 FAILED 故障：预算仍为 1、无终稿、storage failure、原业务阶段有脱敏日志。
- FAILED 保存时 CAS 冲突：返回 conflict，赢家状态保持不变。
- FAILED 正常保存：原业务原因、新版本和数据库一致。
- T2 重写 PASS → COMPLETED、一条 assistant 仍通过。

同时修复回喂阶段丢失 writer 原因的问题：`rerendered` FAIL_SAFE 时不要只保留旧 verifier reason。公开业务码可沿用兼容约定，但内部 stage 必须记录真实 writer reason，不能把未知 evidence ID 记成单纯 verifier 缺覆盖。

DoD：上述新红绿结果可复算，原 equality/ownership/CAS 守卫不变，没有扩大技术 fallback 白名单。

### A2.2 分解修复：两项缺陷减少不代表整体零回归

如果反例成立，采纳前复用现有确定性组装校验，失败保留原候选；不要复制一套漂移的校验器，也不要添加主观争点数阈值。语义诉求保留无法由目前两个指标证明，应撤回“结构上零回归”的绝对描述，交 A3 独立复核。
