## 9. 给接手助手的具体指导

### 9.1 开始时做什么，不要一上来就改代码

按以下顺序完成一次简短核对，记录在新证据目录的一份工作记录中即可，不另建多套规划体系：

1. **确认目录和解释器。**项目根目录与 `backend` 是两个不同工作目录；检查命令的相对路径。使用项目 venv，缺依赖先核对解释器，不直接安装或升级整套依赖。
2. **确认已有修改。**查看 `git status --short`，再比较目标文件与候选清单。哈希变化不代表他人改错；先定位差异并保留。不得把 HEAD 当作本轮修复前的唯一基线。
3. **当前先做 H1，达标后继续 H2/H3。**先写待验证问题：“超时主要来自配置、实际依赖延迟，还是后台收尾缺陷？”不要在诊断前把某个修复方案写成目标；已授权且条件满足的下一阶段无需重复请示。
4. **确认调用链。**沿 `ToolGateway.execute → legal_retrieval.retrieve_laws → 实际检索/重排` 读相关函数和直接调用者，再查看技术失败如何进入 fallback。不要先全仓扫读，也不要只改报错所在的一行。
5. **确认运行状态。**检查自己要使用的端口、对应进程和未决请求。只管理可确认由本次任务启动的进程；不要批量停止所有 Python/uvicorn 进程。
6. **确认证据保存位置。**新建唯一目录，使用拒绝覆盖的创建方式；保存目标文件快照、命令和结果。新日志不能写回历史 `full-tests.txt` 或旧 sessions。

启动前给用户一条简短说明，写清正在验证哪个问题即可。已授权的局部修复不必逐步重复请示；范围外改动、额外费用或生产操作才需要重新确认。

### 9.2 我会怎样排查这个超时

下面是按需使用的排查菜单，不是每项都要新增埋点的任务清单。先检查外层超时与远程请求的关联；现有证据无法解释时，再扩展观察：

| 观察点 | 要回答的问题 |
|---|---|
| 工具提交、工作线程开始 | 排队是否消耗了 8 秒？计时起点到底在哪里？ |
| 本地 embedding、向量/BM25 查询 | 冷启动或锁等待用了多久？暖机后是否仍会超时？ |
| 每次 rerank 开始、结束 | 是哪个 run/请求/阶段发起？是否在外层已到期后才启动？ |
| gateway 超时返回 | 返回了什么状态？底层 future 此时运行中还是尚未开始？ |
| fallback 开始 | 与上一工具工作是否重叠？是否重新执行同一查询？ |
| 后台任务最终结束 | 容量何时释放？有没有晚到结果覆盖已保存终态？ |

新增计时使用单调时钟，日期时间用于日志关联。复用现有 run/request 标识，按诊断需要补阶段和耗时；只有需要辨别查询是否相同时才增加摘要。不要输出 API Key、认证头、完整 `.env` 或真实用户全文。

**区分观察与推断。**“8 秒外层超时”和“某次远程重排耗时 11.86 秒”是已有证据；“所有超时都是重排造成”“两次请求一定相同”还不是。先补缺失的关联数据，不为推断编造日志。

修复方案先从最小改动考虑：已有接口能传递时限就复用；确需扩展时只扩到直接调用边界。不要新建调度平台、全局 deadline 单例或多层适配框架。共享检索路径的默认行为必须被明确考虑。

若证据支持传递 deadline，使用单调时钟计算剩余时间，在新阶段开始前检查，并限制该阶段等待。注意连接/读取超时不等于整次请求总截止时间，SDK 重试也消耗时间，`future.cancel()` 无法强停运行中的同步线程。允许有限后台收尾的方案，应验证容量释放和终态保护；不能声称底层工作严格在 N 秒内全部结束。

方案取舍只需在工作记录中说明依据、影响及测试，不另建 ADR、接口框架或配置体系。若已有需求未约定精确响应时限，可给出基于测量的局部配置建议及限制，不编造产品 SLA。

### 9.3 怎样写测试才不会又测偏

本轮曾发生过“想测 Planner，实际被终稿门短路”的夹具错误。接手至少执行以下检查：

- **先证明到达目标边界。**断言真实工具提交、目标阶段开始或外部尝试次数；仅断言最终错误码不足以说明测到了目标问题。
- **让反例为预期原因失败。**先运行新测试、读取完整失败信息，再改生产代码。ImportError、夹具异常、未进入分支，都不能算业务反例成立。
- **验证相关副作用。**根据改动选择持久化版本、预算、终态、消息、外呼次数或工作容量的断言，无需每条测试检查全部项目。
- **优先用同步信号控制顺序。**通过事件或可控替身制造“内部已开始、外层到期、内部随后结束”；少用长时间 sleep 和苛刻的墙钟断言。测试结束在 finally 中释放阻塞并确认线程收尾，避免挂住下一条测试。
- **按改动选择场景。**时限调整检查边界和成功路径；新增截止检查才补到期前拒绝启动；改变线程收尾才补容量/晚到结果；改变重试才补请求次数。复用既有回归，不把这些场景扩成与改动无关的测试工程。
- **期望值来自约定。**预算期望取自输入配置；调用次数取自允许的重试规则；不能调用被测实现生成自己的预期答案。
- **测试失败后分类再处理。**先区分实现错误、测试错误、环境错误、已有无关失败。修复后重跑相关检查；完整套件不自动循环重试。一次完整成功后，只有新的变更或未解问题才支持重复运行。

如果同一问题连续三次修改仍不能解释失败，停下重新审视调用边界和根因，不追加第四个补丁硬顶。

### 9.4 恢复付费验证时的操作细节

**下一轮采用一个付费执行者、一个服务进程、顺序案例。**guard 只有进程内状态，分别启动两个限额相同的进程可能越过累计预算。本次没有并行评测需求，不开发跨进程计费系统。

每轮付费调用前，依次确认：

1. 新候选离线通过，待执行文件哈希与该候选一致；模型、端点、题集、输出目录和剩余预算已记录。
2. 原账本无未决预约；若有未知服务端状态，保留其最坏费用并停止重复请求，不能因为客户端没收到结果就退款或重跑。
3. guard 限额已按累计费用设置；复用现有离线测试，只有接线或预算逻辑变化才补相关反例，证明超限时没有发出 HTTP 请求。底层重试和 fallback 的 HTTP 尝试都应计入；同时遵守第 7 节关于 guard 会截断部分分支的限制。
4. 当前模型价格及最大输出/思考 token 仍支持预约金额。旧文档的“2 元一次”和“免费重排”不能永久沿用；模型、区域、计费或输出上限变化时重新核对。拿不到 usage 时不能按零费用结算。
5. 环境明确加载后端配置。根目录与后端 `.env` 不合并猜测；不打印密钥。记录真正送出的模型名称，不能根据进程名推断模型。
6. 服务 ready 后先发 C01 的一个新 run，结束并核对持久化和账本后，再按 H3 顺序继续。终端暂时没输出不是启动第二份 runner 的理由。

在线过程中不修改正在被测的生产代码。发现问题先停止新增请求，确认活动调用完成或按未知状态保留预约，再修改、离线验证并建立新候选。这样才能明确哪份代码产生了哪份答案。

### 9.5 如何判断该继续、该停止

| 情况 | 正确处理 |
|---|---|
| HTTP 200、有文本，但 `agent_completed=False` | 记录 Agent 未完成；识别 fallback，不能计成功 |
| runner 退出码 0 | 只说明采集正常结束，继续检查案例结果 |
| 原 judge 为 False，但尚未做语义复核 | 保留机械结果；独立复核未完成，不修改 judge 把它变绿 |
| 离线测试通过，真实调用仍超时 | 保留失败样本，继续定位真实依赖边界，不立即扩大题集 |
| 预算不足以覆盖下一次最坏调用 | 停止付费工作，完成已有证据分析和报告；不得提高额度 |
| 发现服务端状态未知 | 停止对应队列和重复调用；保留预约及未知状态标记 |
| 正在评测的源文件、配置或题集被修改 | 暂停新增付费请求，核对差异及进程实际加载版本；保留在途调用费用和已有材料，不直接杀进程。无关文档变化不触发此规则 |
| 发现范围外的问题 | 记录位置、影响和证据；继续当前可独立完成的任务，不顺手重构 |
| 简单局部实现有几种方案 | 根据现有接口和反例选择最小可验证方案，不为常规取舍反复请示 |

停止某条依赖工作不等于停止全部工作：例如付费调用不能继续时，仍可整理日志、分析反例和完成离线验证。最终报告必须指出具体阻塞，而不是笼统说“需要用户确认”。

### 9.6 交付时请按这个格式自检

只需一份简洁报告加原始证据，不必继续扩写交接文档。报告应回答：

1. **发现了什么：**触发条件、观察结果、代码位置，区分已证实根因和假设。
2. **改了什么：**文件与行为变化；为何该改动足够，以及共享路径是否受影响。
3. **怎样证明：**代码修复提供有效反例和回归结果；纯诊断如实标注未改代码。附命令、退出码及相关候选哈希，失败、未运行与历史结果分开。
4. **真实表现如何：**Agent 是否完成、是否 fallback、语义复核哪些 PASS/FAIL/REVIEW，不用回答长度充当质量。
5. **花了多少：**本轮及累计用量、标价估算、未决费用、剩余限额，区别于供应商账单。
6. **现在留下什么：**服务/进程状态、未决请求、需接手的问题、明确下一步。未经授权不部署、不提交、不推送。

建议每完成一个小目标就核对“结果是否仍解决原问题”。不要把“行数减少”“调用成功”“测试数量增加”替换成原目标。我们要证明的是 Agent 在实际依赖条件下有界执行、正确保存状态，并在有证据时给出合格回答。
