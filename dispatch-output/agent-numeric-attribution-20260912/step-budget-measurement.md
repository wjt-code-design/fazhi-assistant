# 步数测算：5 争点场景的最小步数需求（2026-09-12）

承接 `alignment-20260912-step-budget.md`（grilling 第 3 支：先离线量最小步数，再选手段）。
**零付费、零代码改动**。这是测算报告；若结论是"降开销不足"，按预置分支回来请用户拍板。

## 1. 测量模型（从代码与两条真实轨迹导出，并用后者校验）

- `steps` 计数 = **状态转换次数**（`state_machine.transition()` 每次 `+1`；`state_machine.py:56-57`）。
- 每个持久化检查点 = 一次转换（DB 里 `agent_steps.state_version` 逐次 +1）。
- `register_action` 递增的是 `tool_calls`，**不**递增 `steps`（`state_machine.py:72-79`）。
- 工具调用前闸门：`registered.steps + 3 > max_steps` → 停止（`controller.py:603`）。
  ⇒ **发起检索时必须还剩 3 步**。

**校验 1（H3 轮，4 争点）**：DB 轨迹 v1 bootstrap → v2/v3 检索① → v4/v5 澄清 → v6/v7 检索② → v8/v9 澄清 →
v10/v11 检索③ → v12 conditional(DRAFTING) → v13 coverage 回喂 → v14 失败。
= **14 个检查点 / steps=13** ✓ 与 DB 完全一致。

**校验 2（第 4 轮，5 争点）**：v1 bootstrap → 4 次检索（8）→ 2 次澄清（4）→ 2 个 backfill（2）→ v16 stop。
= **16 个检查点 / steps=15** ✓ 与 DB 完全一致；第 5 次检索发起时 steps=14 → 14+3=17 > 16 → 被拒 ✓。

两条真实轨迹都与模型吻合 ⇒ 模型可信。

## 2. 测量结果

### 5 争点 + 2 澄清 + 成功路径（理想序：无 backfill 检查点、无 coverage 回喂、无 replan）

```
1  bootstrap
2  tool_call(①)        3  tool_result(①)
4  clarification        5  user_fact
6  tool_call(②)        7  tool_result(②)
8  clarification        9  user_fact
10 tool_call(③)        11 tool_result(③)
12 tool_call(④)        13 tool_result(④)
14 tool_call(⑤)        15 tool_result(⑤)
16 conditional_analysis → DRAFTING
17 finalize → COMPLETED
```
= **17 次转换**？ 不 —— 精确数一遍：bootstrap 不计为转换（`steps` 从 0 起），上表 2..17 共 **16 次转换**
⇒ **steps = 16 = max_steps，余量 0**。

且第 5 次检索发起时 steps=12 → 12+3=15 ≤ 16 ✓（不被拒）。

### 结论表

| 争点数 | 最好情况步数 | `max_steps=16` 下 |
|---|---|---|
| 3 | 12 | 可达，余量 4 |
| 4 | 14（无回喂）/ 16（含一次 coverage 回喂） | 可达（H3 实测到 14 后因 writer 失败，非预算） |
| **5** | **16（零余量）** | **仅当：无 backfill 检查点 + 无 coverage 回喂 + 无 replan** |
| 6 | 18 | **不可能** |

### 关键推论

1. **A1（去掉 backfill 独立检查点，省 2 步）只能把失败点后移**：5 争点在"理想序"下才能擦线通过；
   一旦发生任何一次 coverage 回喂（+2）或 replan（+1）或 backfill 检查点（+1），必然失败。
   而前三轮真实运行**恰恰都发生了** coverage 回喂或 writer 失败 —— 这不是小概率。
2. **A3（早期扇出全部检索）能消掉 backfill 检查点**，但 planner 的决策顺序是模型驱动的，
   **无法保证**它一定先检索完再澄清 —— 所以 A3 不是"可依赖"的修复，只是"概率上更好"。
3. ⇒ **"不动上限，只降开销"无法达成目标 A（5 争点稳定出终稿）**：最好情况零余量，现实情况必挂。
   这触发了对齐第 3 支的预定分支：**降开销不足，回来请用户拍板**。

**我的推荐：B-1**，理由：
- 预算上限是一个**产品参数**（`settings.agent_max_steps`），不是法律/证据红线；
- 交接文档禁止的是"**借此**（为通过评测）提高硬上限"—— 而现在的情形是**为消除确定性缺陷**调整参数，
  且我会把它作为**显式、可审计**的配置变更记录（并同步修订交接文档红线条款）；
- B-2 是我明确不推荐的：零余量 = 把"能不能出稿"押在模型不回喂上。

若选 B-1，我需要你给的只是一个数：`max_steps` 提到多少（我建议 **20**：覆盖 6 争点 + 一次回喂）。
