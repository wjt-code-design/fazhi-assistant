# grilling 对齐结论：步骤预算卡点（2026-09-12）

形式：grilling（逐支追问；每题先给推荐再由用户定）。可查的事实我自查，未占用你的决策。
承接 `alignment-20260912-writer-bottleneck.md`，但**课题不同**：上一份是 writer 校验，本份是**步骤预算**。

## 事实（自查结论，全部有代码/DB 出处）

- 拦截点 `controller.py:603`：`if registered.steps + 3 > registered.budgets.max_steps:` → `stopped` /
  `budget_exceeded:step_preflight`。语义 = **发起检索时必须还余 3 步**（留给"评估→起草→落盘"）。
  `max_steps=16` ⇒ 只有 `steps ≤ 13` 时才允许发起检索。
- `steps` 在**每次状态转换**时 +1（`state_machine.transition()`）；`register_action` 增的是 `tool_calls` 不是 steps。
- 第 4 轮付费 run 的账（DB 逐步可复原，**正好卡死**）：
  bootstrap 1 + 4 次检索×2 = 8 + 2 次澄清×2 = 4 + 2 次 `backfill_retrieval`×1 = 2 → **15 / 16**；
  第 5 个争点（诉讼时效）的检索需要再 2 步 → 被 `+3` 预留拒绝。
- **系统级洞察**：历轮 `state_version` = 14 / 14 / 17 / 16，上限 16 ⇒ **主链路长期贴着预算上限跑**，
  四轮四种终态很可能是**同一约束的不同切法**，不是四个独立 bug。
- **A1（去掉 backfill 独立检查点）单独做，余量为 0**：省 2 步后第 5 次检索可发起（13+3=16 ≤ 16），
  但随后 tool_result→DRAFTING→COMPLETED 正好用满 16；任何额外转换（coverage 回喂 / replan / 重复动作）
  都会再次撞上限 —— 很可能只是把失败点从"检索前"挪到"起草后"。

## 五支决策（已定）

1. **目标** = **先让「规划出 5 个争点」时也能进入起草**（不再 `AGENT_BUDGET_EXCEEDED`）。
   范围刻意收窄；这是后续一切 writer 侧验证的前提。
2. **授权边界** = **不动 `max_steps`/`tool_calls` 硬上限**，只做「同等工作、更少步骤」。
   （交接文档明禁"借此提高硬上限"；如需改成，必须用户另行显式授权并同步修订该条红线。）
3. **手段** = **先零成本离线量出最小步数**，再据结果选 A1（去冗余检查点）或 A1+A3（批量检索）。
   测算本身即要交付的离线反例；**不接受"刚好够、一碰就碎"的交付**。
4. **争点数不约束**：保留 planner 的法律判断自由（冻结案例的 `required_issues` 是最低要求不是上限）；
   若按"正好 5 个"调预算，6 个又会挂 —— 正确姿势是降低**每次检索的开销**，使预算对争点数增长更鲁棒。
5. **验证口径沿用先前对齐**：离线反例（watch-it-fail 先红）+ 全量回归 + lint/format/mypy
   → 付费跑 1 轮 → 出终稿再续跑到 **连续 3 轮全绿**；**连续 2 轮同类失败即停**。

## 下一步（待开工）

**零成本**：在现有测试夹具里构造「5 争点 + 2 澄清 + 起草」场景，量出走到起草并落盘所需的**最小步数**
（含最坏情况一次 coverage 回喂），据此判定：
- 若降开销后有真余量 → 做 A1（+A3）；
- 若仍不敷 → **不擅自改上限**，带测算数据回来请用户拍板（届时可能要重新审视第 2 支的授权边界）。
